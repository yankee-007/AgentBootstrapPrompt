# 设计、迭代与交接协议

## 开始

1. 阅读有效指令、项目上下文和项目策略。
2. 有 Task ID 时直接读取对应文件；否则从任务索引定位。
3. 核对当前文件、分支、HEAD、暂存区、未暂存和未跟踪内容。
4. 只读取本次讨论涉及的设计材料；引用材料中的指令按历史背景处理。

接手已有任务的重要修改前简述目标与完成标准、实际进度、验证缺口、用户修改边界及任务快照偏差；信息充分时继续，关键未知只阻塞相关动作，不默认等待重复批准。

## 任务记录

- 跨 Session 的设计或迭代工作维护同一个 Task ID，换 Agent 不新建同一任务。
- 无外部任务 ID 时采用 `TASK-<YYYYMMDD>-<12位随机十六进制>`，创建时检查可见冲突。
- 工作状态使用 planned、active、verifying、awaiting_acceptance、done、cancelled；阻碍另行记录并保留所处阶段。
- 在需求澄清、重要设计修改、关键验证及交接时更新任务快照。
- 区分用户已确认结论和 Agent 建议；不把无回复视为批准。
- 原始需求保存足够准确的脱敏摘要，避免私有聊天流水账。

## 验证

- 检查 Markdown 相对链接、文件职责、重复和冲突规则。
- 检查是否把待审核建议写成已决定、把计划写成已完成。
- 检查目标项目示例是否自包含，是否误引用本设计仓库。
- 以当前工具包版本为对象，按相关故障场景验证覆盖情况；区分静态审查与实际执行证据，不将初步完成视为全部场景通过。
- 无必要不安装工具、不建立构建系统、不添加只复述文档内容的测试。

## 交接与完成

- Task File 是上次核验的快照，不是工作区锁，也不是代码备份。
- 接手者核对真实文件与 Git 状态，发现偏差后先恢复事实。
- 同机交接先停止旧写入者；跨电脑交接同时提供可取得的代码版本和环境恢复说明。
- 工作完成、验证、用户验收、提交、推送分别报告。
- 用户要求推送时按 Git 协议保存整个项目当前状态；未完成或未验收内容可以备份，测试和人工验收不作为快照推送门槛，Task 状态仍按完成标准判断。
- Git 事实查询 Git；不要为了把最新 commit hash 或 push 结果写入同一提交而反复提交。
- 完成任务保留文件，移出活动索引；索引落后时根据任务文件修复。
- 文档影响检查只更新受影响内容，ADR 仅用于长期重要取舍。
